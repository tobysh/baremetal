# Security model

Last reviewed 10 November 2026. Baremetal runs untrusted code from anonymous visitors, so runner isolation and the sandbox outweigh everything else. Production requires a separate runner socket service; systemd host verification is still pending. The IDs below (L1, R1, ...) are the audit finding labels used in code comments and regression fixtures. Host-level setup is in `docs/deployment-hardening.md`; the system overview is in `docs/architecture.md`.

## Assets and attackers

Assets: the web server host (shared kernel with the separately configured runner service), MongoDB, accounts (scrypt hash, TOTP secret, sessions), learner data, XP/leaderboard integrity, hidden tests and reference solutions, the `ANTHROPIC_API_KEY` budget, `AUTH_SECRET`. Attackers: anonymous visitor, signed-in learner, a learner with a stolen password, a cross-site page, a hostile network position between proxy and app. Out of scope: host OS hardening beyond the app, third-party services, legal review.

## What is in place

**Sandbox (`src/lib/runner-engine.ts`).** bubblewrap with no network, `--disable-userns`, an x86-64 seccomp denylist (ptrace, bpf, io_uring, userfaultfd, perf_event_open, mount family, kexec, module loading, namespace calls, `fsopen`/`fsmount`/`move_mount` and similar), rlimits, 5 s timeout, output caps. Compilation runs on size-capped private tmpfs with read-only sources; only the executable is returned, over a pipe capped at 64 MiB. Run directories are read-only; `/tmp` and `/dev/shm` are capped. Queue admission is capped per user and per IP, a signed-in account holds at most one compile slot at a time, free slots go to the waiting owner served least recently rather than the oldest request, every compile (each `set`-case recompile included) counts against a per-owner budget (`RUNNER_COMPILE_BUDGET`, 60 a minute), slots are handed directly to waiters, jobs cancel on request abort, and at most 24 may wait (503 beyond). Runner boot cleans only old workdirs. Production web handlers call a versioned Unix-socket service with bounded requests/responses; the service resolves its own exercise definitions and owns admission and cancellation. The socket accepts only the web execution group; its logs exclude source and identities. Optional per-job cgroup v2 limits via `RUNNER_CGROUP_ROOT` (untested on a real host, see deployment doc).

**Result integrity (L1, L2; R1-R5).** Lessons with a `tests.*` harness decide pass or fail in the learner's process. C lessons with a `driver.c` use an out-of-process verdict (R5); everything below R5 describes the harness path, which every other lesson still uses.
- R5 (out-of-process verdict, C `driver.c` lessons; first converted: `c-memory/pointers-swap`, `c-memory/arrays`, `c-data/arrays`). The learner's `main.c` is compiled alone to an object in a directory that holds nothing else; the driver (`VERDICT_PRELUDE` from `src/lib/verdict.ts` plus `driver.c`) is a separate translation unit, so no learner macro or include reaches it and `guardSharedSource` is not needed. The driver object and a reference program (driver linked with `solution.c`) are built once per lesson content (sha256 of prelude, driver and solution), ownerless (not charged to the learner's compile budget or cancelled by their disconnect), and only successful builds are cached, so a broken reference fails the lesson closed. Each attempt draws 16 bytes from `crypto.randomBytes`. The learner's linked program and the reference each run alone in their own sandbox with that seed on fd 4; a `.preinit_array` hook (before any constructor) reads and closes it, moves the result pipe to fd 3 and wipes its copy of the seed. The driver writes typed records to fd 3 with raw syscalls and its own formatting (no libc calls a learner could interpose): a check header (fixed or seeded, name), inputs and observed values (integers in decimal, doubles as hex bit patterns, strings and bytes as length plus hex, arrays as length plus elements, structs as named fields only), then an end record. The server parses both transcripts and compares them check by check: a missing, extra, renamed or reordered check, changed inputs, a record after the end, a crash, a timeout, UBSan or a non-zero exit fails; a crash fails the check in progress and every later one. Failure messages show the input and the learner's values; expected values only for fixed edge cases. Neither the driver nor the solution is in the learner's sandbox or in the public exercise (`toPublicExercise`). The learner still controls its whole process, including fd 3, but a transcript only passes if it equals the reference's for inputs from a seed it could not know in advance, which means computing the right answers. `fixtures-forgery.mts` replays a full transcript from another seed, hardcodes every fixed edge case, writes extra or early-end records to fd 3, and tries to read the driver, the solution and the seed at compile and run time.
- R6 (stdout lessons): only the first failing case of a run returns its expected output; later failing cases return the learner's output and a note. The `set` variants and stdin cases would otherwise hand over every answer, which a learner could hard-code. `scripts/security/audit-checks.mts` asserts at most one case returns `expected`.
- R1: `testExercise` requires the exact ordered test names the reference solution produces (`expectedTestNames`), fails closed if the reference is unavailable, and requires matched C/kernel RUN/result events and a zero normal exit.
- R2: C/asm results carry a per-run nonce passed in `BM_NONCE`, taken in a `.preinit_array` hook with randomized identifiers and wiped from the environment.
- R3: hidden-source leaks are blocked by a scan and diagnostics located in harness code are redacted (Rust: any primary or secondary span or numbered source line past the learner's lines; Go: any `bm_test.go` location, including ones named inside a learner-file diagnostic). Test binaries run with only themselves in the work dir. The scan (`TAMPER_PATTERNS` plus `TAMPER_PATTERNS_BY_LANGUAGE`, chosen by the exercise language) covers the shared patterns (result protocol, `#include "..."`, `include_str!`, `go:embed`, `.incbin`, `/proc/self`) and, per language:
  - Rust: the identifiers `include`, `include_str` and `include_bytes` anywhere (so `include_str !(..)` and macros that forward the name are caught; a comment containing the bare word "include" is rejected too), and `#[path = ..]`.
  - Assembly: `.incbin`, `.include` and the `*_array` section directives in any case, and `.macro`/`.altmacro`/`.irp`/`.irpc` (no lesson uses them; they can assemble a directive name from parameters).
  - C and kernel: `#embed` and `__has_embed` (C23; GCC 15+ accepts it, so it would read `main.c` with the harness appended), and `__has_include`/`__has_include_next` (no lesson uses them; they tell which files sit beside the build, which gated a directive to the real build). `\binclude\b` is deliberately not used for C. The `__has_include` ban is only a first filter: token pasting (`P(__has_, include)`) still spells it, so the real-build check below is what stops it.
  - C and kernel also pass `guardSharedSource` (`runner-engine.ts`), because their harness is appended to the learner's file. The learner's file (plus an end-of-file sentinel) is preprocessed and compiled alone in an empty sandbox directory. Any `#include` that opens a file fails there, and the sentinel errors on a self-include, so `#define F "main.c"` / `#include F` is rejected. The emitted assembly is scanned (any case) for `.incbin`, `.include`, `.macro`, `.altmacro`, `.irp`, `.irpc`, `.rept`, `.reptc` and the `*_array`/`.ctors`/`.dtors` sections, which catches `asm(".inc" "bin \"kernel.c\"")`. It also runs `gcc -dM -E` on the learner's file and on its `#include <...>` lines alone; every macro the learner's text defines or changes (`#define if(c) if(1)`) is `#undef`'d before the harness, and macros from system headers that were changed are restored. Names the lesson's own starter defines (for example `COM1`) are left as the learner wrote them, because harnesses use them. This is still one translation unit: the structural fix (harness as its own object, as for assembly) is not done for C and kernel because struct-testing harnesses would each need to declare the learner's types.
  - The guard's standalone build can differ from the real one (a file only one directory holds, a macro only the real flags define such as `__SSP_STRONG__`), and a directive emitted only in the real build used to be assembled unseen and embedded the whole harness, including the kernel nonce. So the real test build is itself checked (`compileToAssembly`): the combined source (learner + harness, real flags and `-Dmain`/`-Dkmain` renames) is compiled with `gcc -S` in a directory holding only that file; every dependency gcc records (`-MD`) must be the source itself or a plain path under `/usr` (no `..`, so `#include </dev/null>` or an absolute path back into the work dir is rejected); and the emitted assembly is scanned, raw and with C comments removed, for `.incbin`, `.include`, `.macro`, `.altmacro`, `.irp`, `.irpc`, `.rept`, `.reptc` (the `*_array` sections are left to the guard because the C prelude uses `.preinit_array`). That exact assembly is then fed to `as` on stdin and linked in a directory that holds no source (C: `bm_init.c`; kernel: `boot.S`, `runtime.c`, `link.ld`), so a directive the scan misses has no harness file to open. What is scanned is byte-for-byte what is built. `scripts/security/audit-checks.mts` probes this (both `__has_include` directions, pasted and plain, and `__SSP_STRONG__`).
  - Assembly is also built structurally: the harness is compiled to `harness.o` first, `starter.s` is assembled alone in a separate work dir that holds nothing else, and the objects are linked afterwards. The learner's assembly can't read the harness at build time even if a scan pattern is missed.
  - Rust still has the harness appended to the learner's file, so a missed spelling would leak it. C and kernel share a translation unit too, but their build no longer has a harness file reachable from the assembler (above); a preprocessor-level read of the combined source would still have to get past the dependency check. Options evaluated for a structural fix (not implemented):
    1. *Source on stdin* (`rustc -`, `gcc -x c -`): no file holds the harness. Tested on the host: `include_str!("/dev/stdin")` and `/proc/self/fd/0` read 0 bytes because the pipe is already consumed, and `#include "/dev/stdin"` is empty. Costs: diagnostics say `<stdin>`/`<anon>` instead of `main.rs`/`main.c` (needs a `#line` prefix for C and a rewrite step for rustc), `exec` takes stdin for compile steps (the C/kernel assembly step uses it), and rustc under bubblewrap needs `/proc` for sysroot detection (check before adopting). Most promising.
    2. *Separate units*: compile the learner's code and the harness separately and link. This needs the harness to call learner functions through declared symbols; most C harnesses do, but Rust harnesses use private items and `#[cfg(test)]` modules, so it would mean rewriting lessons.
    3. *Scan only* (current): cheap, but every new spelling is a bypass until the pattern is added, which is how the Rust spacing and macro, asm upper-case and C23 `#embed` variants were found. `fixtures-forgery.mts` holds each of them.
- R4: first-pass XP is limited by an atomic per-user pace and a rolling 24 h cap; minimum solve time applies only with a known start. Suspect passes are saved without XP (`xpWithheld`, flag `xpPending` on interrupted decisions); review with `npm run flagged-accounts`.

**Practice answers.** `POST /api/practice` needs a session, the same-origin check and a per-user limit (120 per 10 min), caps the body at 32 KB, and validates the submission shape and that every chosen line or token belongs to the exercise. Answers live only in `practice.json` on the server; `toPublicPractice` omits answers, the canonical order, blank values and the explanation, and a wrong answer returns only a count. A non-canonical parsons or blanks arrangement is judged by the lesson's hidden tests through the normal runner path. XP goes through `recordAttempt` with the same pace limit, 24 h cap and solve-time floor, at a quarter of the lesson's XP.

**Auth.** scrypt with its parameters stored in the hash (`scrypt$N=131072,r=8,p=1$salt$key`; older `scrypt$salt$key` hashes made with N=2^15 still verify and are rehashed on a successful login, and parameters are bounded when parsed), hashed session tokens, httpOnly SameSite=Strict cookie named `__Host-bm_session` and `Secure` (names and flags in `src/lib/session-cookie.ts`; `BM_INSECURE_COOKIES=1` drops both the prefix and `Secure` for plain-HTTP development in browsers that refuse Secure cookies on localhost), sessions that last 30 days (administrators 12 hours) and die after 14 days unused (administrators 2 hours; `lastSeenAt` is touched at most every 5 minutes), a token that is replaced after 24 hours from a server action (`rotateSessionIfDue`; the old record lives 60 seconds for parallel requests and only one of two racing calls wins), a new login that deletes the browser's previous session, reset links read only from the URL fragment (the old `?token=` form is ignored), reserved usernames blocked including digit/symbol lookalikes and as substrings of words such as admin or baremetal (`isReservedUsername`), `updateProfile` and `updateRhythm` limited per user, `/api/admin/stats` limited per admin (30 per minute), analytics `path` accepted only for real pages, TOTP with replay protection, HMAC backup codes (legacy single-use still accepted), atomic password/OTP attempt reservations, pair-scoped lockouts, a per-account delay independent of IP (after 15 failures in an hour each further failure doubles the wait from 30 s up to 15 min, for any address and whether or not the account exists; cleared by a correct password), PoW CAPTCHA (challenges are signed over the requesting IP and the form, so a solution works only for that IP and form; up to 400,000 hashes), HIBP and common-password checks, password required to enrol or disable 2FA, Settings second-factor checks (change password, backup codes, disable 2FA, delete account) go through the same per-user OTP guard as sign-in and have their own per-IP bucket (`settings-2fa`), `changePassword` requires a code when 2FA is on, email verification at signup (legacy accounts without the flag still work), generic signup/reset responses, fragment-based reset links, encrypted durable email queue (one pooled SMTP transport with timeouts, one drainer at a time guarded by a database lease, at most 10 queued messages per recipient per hour for every caller, CAPTCHA on signup and forgot-password). `safeNext` is in `src/lib/redirects.ts`.

**Admin panel.** Pages and every server action call `requireAdmin` (role plus 2FA) on the server. Actions are rate limited per admin (120 per hour), cannot target admin accounts or the caller, and are logged in `admin_audit`. Bans and deletions require typing the account's email. Admins cannot read or set passwords; the security log shows keyed IP hashes, not addresses. Accepted limitation: an admin can lock or ban any non-admin account without a second approver, so keep the admin list short.

**API and tutor.** Type and size checks come before quota. The tutor never sees the reference solution, learner text is tag-escaped, replies stream through `SolutionGuard` (`src/lib/tutor.ts`), which holds back the last window of tokens until every window containing them has been compared with the solution, so a solution excerpt never reaches the client (on a match the rest of the reply is replaced by the fallback sentence and the reply is not cached). Before comparing, text is NFKC-folded and stripped of non-ASCII characters (zero-width and soft hyphens included), and every non-keyword identifier becomes one placeholder, so renaming variables does not help; each reply is checked both with comments stripped and with them kept (a comment is still visible text). The window is 24 tokens, or about half the solution (minimum 10) for a very short one, and it also spans the thread's earlier assistant replies, so a solution split across turns is caught. Comment stripping covers `/* */` and `//`, plus `;` and `#` line comments when the lesson language is assembly (string literals are left alone). Checks: `scripts/tutor/stream-guard-checks.mts`, `scripts/tutor/leak-checks.mts`. Learners never see the Ollama host, model name, raw Ollama errors or environment variable names: those go to the server log and the learner gets a generic unavailable message; Ollama calls have a deadline (`OLLAMA_TIMEOUT_MS`, default 120 s) and malformed response lines are treated as an outage, newcomers (unverified or very new) draw from a pool that reserves capacity for established users, DELETE is rate limited. A tutor call that has reached Anthropic is billed whatever happens next: the route reads `input_tokens` (and cache tokens) from the stream's `message_start` event and, if the client disconnects or the stream errors, keeps at least that cost in the dollar budget, and the hourly/daily quota is refunded only when the call failed before reaching upstream (`scripts/tutor/abort-checks.mts`). Hints are served only by `/api/hint`, which requires a session and records use (the tutor sees only the hints the learner has unlocked); public exercises carry `hintCount` only. Per-question `tutor_usage` rows carry an `owner` HMAC of the user id (never the id) so they can be exported and deleted with the account; older rows have none and expire after 180 days. Tutor and analytics IP keys and console identities use keyed hashes. Both Markdown renderers pass executable-markup fixtures. Production dependency audit: zero advisories (29 Oct 2026).

**Interactive shell (Firecracker microVMs).** Optional, off until the host is verified. The web process never touches Firecracker: it talks to a broker (`scripts/shell-broker.mts`, unprivileged user, session tokens bound to the account, nothing stored in the database) which talks over a Unix socket to the launcher (`scripts/shell-launcher.mts`). **The launcher runs as root**, because the jailer needs chroot, pivot_root, mknod, setuid and cgroup access; the unit (`deploy/systemd/baremetal-shell-launcher.service`) shrinks that with a capability bounding set (SYS_ADMIN, SYS_CHROOT, SETUID/SETGID, MKNOD, CHOWN, FOWNER, DAC_OVERRIDE, SETPCAP), a syscall filter, `MemoryDenyWriteExecute` with `node --jitless`, no network, read-only system and a resource slice. Only members of `baremetal-shell-launch` (the broker) can reach its socket, so a compromise of the web process still has to get through the broker's request validation to ask root for anything. Learners get a microVM with its own kernel (KVM), no NIC unless a lab drop-in adds one, a per-session copy of the rootfs, a per-VM cgroup, and a numeric uid from a reserved range. Not yet verified on a real host: the capability set and syscall filter are derived, not minimal; `DelegateSubgroup` plus `ProtectControlGroups=private` placing VM cgroups under the slice; Firecracker under MDWE; SMT side channels between learners (`nosmt` recommended). Run `scripts/shell/hostile/` and the first-start checks in `docs/shell-deployment.md` before enabling the web endpoint. A guest-to-host escape would land as the unprivileged jailer uid, but a launcher bug would be root.

**Shared addresses (trade-off).** Runner admission, the tutor IP quota and the auth limits no longer treat one IP as one person. Signed-in runs are admitted per account only, the tutor's per-IP quota applies only to accounts under 24 h old, and sign-up/sign-in per-IP limits are 30 and 60 per 15 min. Abuse from one address is therefore bounded by per-account limits, the dollar budget, the per-email limits and the CAPTCHA rather than by a tight per-IP cap. Anonymous traffic keeps its per-IP limits. Values: `docs/deployment-hardening.md`.

**Proxy.** Production refuses to boot without a valid `TRUSTED_PROXY_HOPS`; short `X-Forwarded-For` chains land in a strict per-process "unknown" bucket (L3). In production `sameOrigin` compares the complete origin (scheme, hostname and port) against the configured site URL and never trusts `X-Forwarded-Host`.

**Content Security Policy (`src/lib/csp.ts`, `src/proxy.ts`).** Pages get `script-src 'self' 'nonce-<per request>' 'sha256-…'` with no `'unsafe-inline'` or `'unsafe-eval'`, plus `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. Nonces alone do not work here: every page is a Cache Components shell prerendered at build time and served as-is, and the Next guide's statement that nonce CSP is incompatible with partial prerendering refers to the scripts inside that shell, which have no request and so no nonce. In Next 16.4 the shell holds only three executable inline scripts (the theme bootstrap, React's `$RT` timestamp and its `$RB`/`$RV` reveal runtime); the Flight data, the Turbopack bootstrap and React's streaming scripts are all emitted by the per-request resume, which takes the nonce from the `Content-Security-Policy` request header the proxy sets. So the proxy allows the shell scripts by hash: on its first request it reads every `.next/server/app/**/*.html`, hashes each executable inline script (about 15 distinct, including the static `_global-error` page) and keeps the set for the process. If any shell cannot be read, or no executable shell scripts are found, it logs an actionable error and returns uncached 503 plain-text responses for pages instead of relaxing the policy. Restore the complete `.next` build and restart the server to recover; partial allowlists are rejected too. External chunks are allowed by `'self'`; `'strict-dynamic'` is not used because the shell's `<script src>` tags have no nonce. Alternatives rejected: forcing every page dynamic (`connection()` in the root layout) gives up the static shells and fails the Cache Components build rule for uncached data outside `<Suspense>`; `experimental.sri` only adds `integrity` to external scripts and does nothing for inline ones. The proxy runs on every page (not API routes, `/_next/static`, `/_next/image` or the metadata files) and still does the signed-out redirect for `/dashboard`, `/settings` and `/admin`. Responses it skips get the static policy from `next.config.ts`, the same with `script-src 'self'` only. Nginx must not add a second CSP or cache HTML (a cached page would replay a nonce).

## Grading trust levels

Lessons are graded in one of three ways, from most to least trusted:

- **Driver (seeded transcript diff):** `driver.c` runs the learner's code and the reference solution with the same random seed and `src/lib/verdict.ts` compares transcripts, so the learner never sees expected values and the verdict is computed outside the learner's process. Used by three lessons in `c-data` and `c-memory`; all other tracks have none.
- **`cases.json` (stdout cases):** the runner compares stdout itself, outside the learner's process. Variable rewriting (`set`) limits hardcoding. Used mainly by `first-steps`, `sec-detection`, and parts of the `sec-*` tracks.
- **Harness (`tests.*`):** the hidden tests are linked or compiled with the learner's code and print the `@@PASS/@@FAIL` markers from the same process. This is the weakest level: the tamper scan (`harnessTampering`) is the main defence against forged markers. Most lessons (all asm, osdev, Go and Rust tracks, most C tracks) use it.

Anything that needs high-trust status (certification, rare achievements) must not rely on harness-graded lessons alone.

Run `npm run audit:grading` for a tab-separated inventory of every published programming exercise, including challenges, or `npm run --silent audit:grading -- --json` for JSON. Rows contain identifiers, language, kind, trust level and whether the verdict shares the learner's process; no hidden code, test inputs or reference answers are emitted. Drafts are excluded by the existing curriculum loader. This inventories grading mechanisms, not demonstrated resistance to every forgery: fixed stdout cases can still be memorised. Practice and recall questions use separate answer checking and are outside this programming-assessment inventory.

## Open limitations (accepted or deployment-bound)

| Item | State |
|---|---|
| L1 same-process forgery | **Resolved** for C lessons with a `driver.c` (R5, 10 November 2026: the verdict is a server-side comparison with a reference transcript under a fresh seed, so forging a pass means solving the exercise; three lessons converted so far). **High** for every other harness lesson and for leaderboard integrity overall (re-rated 10 November 2026: Go and Rust have no nonce and are the easiest to forge; C and kernel have one but share a process and a translation unit with the harness), accepted for now while lessons are converted. A determined C/asm learner can read the nonce and test names from live memory and print a full valid transcript; Go and Rust have no nonce (only exact names); the kernel guest runs in ring 0 and can write the debug console. R1 forces a complete transcript and R4 bounds XP. Fix: convert each lesson to the out-of-process verdict (R5; `docs/content-authoring.md`, "Drivers"). Only C has it so far. Revisit if the leaderboard gains prizes. |
| Runner service deployment | Separate service/client, dedicated systemd users, private network, restricted filesystem and cgroup setup are implemented. Install and verify the units on the real host before public launch. A sandbox escape still reaches the runner uid and the shared kernel; service separation is not a VM boundary. **VM isolation (planned):** run the runner on its own VM or host, with no route to MongoDB and no copy of `AUTH_SECRET`, so a kernel exploit from a learner's program cannot reach the database or the web host's secrets. Until then treat the host kernel as part of the trusted base and keep it patched. |
| Seccomp denylist | The filter denies known-dangerous syscalls and allows the rest. An allowlist (the syscalls gcc, ld, rustc, go and the test binaries need, derived from `strace -f` over `verify:content`) is the stronger design and is not done; a new kernel syscall is allowed by default until the list is updated. |
| Shell public enablement | Production web shell endpoints require both `SHELL_BROKER_SOCKET` and `SHELL_HOST_VERIFIED=1`. The latter is an explicit operator attestation after the deployment guide's host tests; it is not automatic proof that Firecracker is safe. The installation template leaves it unset. Real-host verification remains pending. |
| Per-job cgroups | Implemented (`memory.max`, `memory.swap.max=0`, `memory.oom.group=1`, `pids.max` 128 for runs and 512 for compiles, `cpu.max`), stale `job-*` groups removed at runner start, but never exercised: the dev workspace exposes cgroups read-only. Needs a memory-bomb check on the real host. The runner unit's `TasksMax` must exceed the worst case of every slot compiling at once (`slots x 512` plus the service itself). |
| CSP | `style-src` keeps `'unsafe-inline'` (server-rendered `style` attributes, CodeMirror's injected `<style>`). Script hashes are read from the build's shells once per process; a shell regenerated at runtime with a new inline snippet would be blocked, and `scripts/security/csp-check.mts` is what catches that. `next dev` uses the relaxed policy. |
| Email delivery | At-least-once; duplicates possible after a crash. Signup needs verification mail, so the worker must be installed: enable `deploy/systemd/baremetal-email.timer` (runs `baremetal-email.service` every minute as the web user, with `/etc/baremetal/web.env`: the same `AUTH_SECRET` to decrypt the queue, `SMTP_URL`, `EMAIL_FROM`, `MONGODB_*`). Without the timer, mail stops after a restart. Rotating `AUTH_SECRET` makes queued mail unreadable. Alert on `baremetal-email.service` failing. |
| XP recompute | `recompute-xp` needs `--confirm-backup` (a verified `npm run backup-db -- --verify`) and the site stopped. Each user is planned in memory first and a pending pass with no recorded decision stops that user before any write. Writes use one transaction per user on a replica set; standalone MongoDB has none, so the steps are idempotent and the total is written last (re-run after a crash). |
| Interrupted first pass | `recordAttempt` is a sequence of steps, not a transaction. A crash leaves `xpPending`; `reconcilePendingXp` (`progress.ts`, run at web start and every 10 minutes) finishes passes whose decision is in `xpQuota` or `xp_events`, reverts younger ones with no decision so the next pass awards normally, and reports older ones for `npm run flagged-accounts`. |
| Review-event persistence | Schedule changes atomically retain a `pendingEvent` on their review document. History insertion uses the event's stable ID and acknowledgement clears only that event. Requests, startup and periodic reconciliation replay pending events without moving the schedule again; failures retain recovery intent. Account deletion is rechecked after insertion to avoid resurrecting deleted history. Existing events need no migration. |
| Tutor-budget persistence | The unique `tutor_spend.key` index is required before database initialization succeeds. Durable `tutor_reservations` record hold and settlement decisions; each scope applies a reservation marker and its total change in one atomic write, so partial writes and lost responses can be replayed. Startup/periodic recovery refunds stale unstarted calls and conservatively retains the full hold for stale active calls whose upstream usage is unknown. Only settled journals expire (60 days); unresolved records do not silently expire. Existing totals are retained. Very high custom request quotas can grow daily marker maps towards MongoDB's document limit; writes then fail closed, so monitor document growth when raising quotas. |
| Targeted read-only review | Claude reviewed `achievements.ts`, `rhythm.ts`, `inline-script.tsx` and workspace code. Clearing tutor history bypassed the Unaided check; fixed with a sticky progress flag and an API regression check. Review-reset farming and goal/timezone changes affecting rhythm remain honour-system limitations. This was not a full penetration test. |
| Optional hardening | Session list with revoke, seccomp allowlist instead of denylist. |

## Regression checks

- `npm run test:e2e -- http://localhost:3100` (auth, 2FA, lockout, CAPTCHA, reset, authorization, redirects) against `npx next start -p 3100`.
- `npm run test:unit`: `node:test` suites in `tests/unit/` (`safeNext`, TOTP and backup codes, crypto, rate-limit IP extraction, tutor normalisation, `harnessTampering` once exported). CI runs it with `npm run check:legal`, which compares every `collection("...")`, storage key and cookie name in `src/` with `content/legal/*.md`; bump `SITE.legal.lastUpdated` whenever that folder changes.
- `scripts/security/sandbox-escape.mts` (also `npm run test:sandbox`, CI `verify-content` job): fork bomb, memory bomb, network egress, `/proc` reads, `#include "/etc/passwd"`, `.incbin` via `asm()`, privileged syscalls, Rust compile-time includes and proc-macros, Go cgo and embed, all through `runProgram`. `sandbox.sh` is a wrapper for it.
